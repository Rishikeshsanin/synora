# Synora backend (draft)
Python 3.12. API: `uvicorn synora.api:app --port 8000`. Separate worker: `python -m synora.worker`. Run from apps/api. Dockerfile is Render-compatible; no services provisioned. Fixture mode is synthetic WAV, not AI music. Production refuses fixture and no real provider is enabled. Capabilities endpoint exposes unsupported controls.

## Disposable local test
Use a fresh local Supabase instance or PostgreSQL with Supabase-compatible auth roles and auth.uid(); never a shared or live project. Apply the migration only to that disposable database. CLI unavailable in authoring environment, so migration timestamp selected manually; validate with local CLI before integration. Set:
- SYNORA_ENV=test, MUSIC_PROVIDER=fixture, SYNORA_DISPOSABLE_DB=1
- DATABASE_URL pointing at disposable migrated DB
- MEDIA_SIGNING_KEY a randomly generated secret of at least 32 characters
- API_PUBLIC_URL=http://testserver for tests, http://localhost:8000 for manual use
- MEDIA_DIR a private directory shared by local API and worker
- FIXTURE_TOKENS_JSON a JSON mapping of random development bearer tokens to UUIDs; never use in production.
Run `python -m pip install -r requirements-dev.txt` then `python -m pytest -q`. Integration tests expect an otherwise empty disposable database and serial test execution.

For real auth set SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY and use access token verified by Auth /user. Use dedicated Synora-only database login, with only required privileges in synora schema. Storage adapter uses server-only SUPABASE_SERVICE_ROLE_KEY; provision private synora-private bucket only after approval. No bucket created in migration. Local signed URLs expire in five minutes, and download disposition is signed. Never log signed URL query strings: disable proxy and uvicorn access logs for media routes or redact query strings.

## Wave 3 library contract (proposed to #1 and lead)
`GET /v1/music/library?limit=30&cursor=<last job UUID>` (1–100) returns `{items:[{job:Job,asset:Asset|null,prompt:string}],next_cursor:UUID|null}`. All reads are scoped to the authenticated owner; ordering is created_at DESC, id DESC; cursor must belong to the same owner and visible job, otherwise 422. Queued/running/failed/cancelled items have no asset. Successful jobs include freshly signed playback metadata, not storage keys or user IDs. Download still uses the explicit asset download endpoint. POST /v1/jobs/{id}/cancel returns a Job and is idempotent for terminal jobs; another owner's UUID is 404. No migration required. Existing job/asset endpoints remain compatible.

## Wave 3 fixture orphan reconciliation
In explicit fixture local/test mode only, use `PYTHONPATH=apps/api:. python -m synora.cleanup OWNER_UUID/JOB_UUID/ATTEMPT_UUID.wav [more keys]` (max 100 explicitly identified WAV keys, grace >=600 seconds). It locks the owning job and refuses unknown jobs, live/matching running tokens (including expired tokens not yet recovered), committed/referenced assets, young files, malformed paths and symlinks. Only definitively stale, unreferenced files are deleted. A DB error before verification leaves bytes intact. This is a conservative operator entrypoint, not automated scanning or production storage garbage collection; .tmp and unknown-job files remain manual investigation. Agent 6 owns independent lost-ack tests. Do not use against live resources.

## Wave 5 proposed additive project / recipe API
The existing owner-composite project foreign key is reused; no migration or dependency change. `POST /v1/music/jobs?project_id=<uuid>` attaches a new job to an existing owned project. Missing/foreign project returns identical 404; malformed UUID 422. Omitted project preserves the legacy request hash, existing request/response shape and idempotency behavior. For attached jobs, the project UUID participates in the idempotency hash; changing or removing it under the same key returns 409. `GET /v1/music/library?project_id=<uuid>&limit=30&cursor=<uuid>` filters history, with a cursor required to belong to that project and owner (422 otherwise). Omitted project returns the entire library unchanged. `GET /v1/projects/{id}` returns existing project metadata (id/name/created_at). `GET /v1/jobs/{id}/recipe` returns only `{project_id: UUID|null, spec: MusicSpec}` for the authenticated owner of a visible music job; exact saved public settings, no URL, storage key, credentials or internal provider metadata. Reusing a recipe requires a fresh explicit submission and remains subject to existing rate limits and fixture-only policy. Shared contracts remain lead-owned; this is a candidate API pending ratification. No live migrations or production provider changes.
